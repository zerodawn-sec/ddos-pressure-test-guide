# 压力测试计划模板：从授权到报告的完整流程

多数压力测试失败不是方法问题，而是计划问题：目标定义模糊、窗口选错、没有明确的通过标准。这份模板来自多次实际测试的沉淀，直接复用即可。

## 1. 授权与范围（测试前必须完成）

| 项目 | 内容 |
|------|------|
| 书面授权 | 测试对象归属证明或书面许可，注明IP段/域名 |
| 范围边界 | 明确哪些资产在范围内，哪些绝对不碰 |
| 时间窗口 | 提前约定的测试时段，避开业务高峰 |
| 紧急联系人 | 双方各一个，出问题立即停 |
| 退出条件 | 预设"出现X情况立即中止"的触发器 |

没有这一步，后面所有技术工作都是风险。

## 2. 目标画像（决定方法选择）

动手前先回答四个问题：

1. **入口在哪**：直连IP还是CDN/高防后面？回源路径是什么？
2. **协议栈**：TCP/UDP暴露面、HTTP(S)端点、自定义协议（游戏、数据库）？
3. **资源瓶颈假设**：带宽型（出口打满）还是计算型（连接表、线程池）？
4. **正常基线**：日常QPS、连接数、延迟P95——没有基线就没法判定"劣化"。

## 3. 方法矩阵（按层分配）

| 层级 | 方法 | 验证什么 |
|------|------|---------|
| L4 | SYN/ACK/UDP泛洪 | 带宽清洗能力、SYN cookie是否生效 |
| L4 | 连接耗尽 | 连接表上限、超时配置 |
| L7 | HTTP/HTTPS请求泛洪 | WAF规则、速率限制 |
| L7 | 慢速攻击 | 服务器超时、线程占用 |
| L7 | 协议级（JS/CAPTCHA后） | 真实业务路径的容量 |

每行一个独立测试轮次，不混跑。

## 4. 通过标准（测试前定义）

- **阈值劣化**：核心指标劣化不超过基线的15%
- **恢复时间**：停止测试后N秒内恢复基线
- **错误率**：测试期间5xx占比 < 0.5%
- **降级行为**：超过容量时是拒绝服务还是排队（拒绝优于超时）

## 5. 报告格式

每轮测试固定记录：时间戳、方法、强度、持续时长、观测指标（带宽/连接/延迟/错误率）、截图或日志摘录、结论。

最终报告三段式：**执行摘要**（一页，给管理层）→ **方法与数据**（给技术团队）→ **修复建议**（按优先级排序）。

## 6. 常见坑

- 只测峰值不测持续：清洗设备能扛30秒峰值，扛不住30分钟持续
- 忘了测恢复：出事时恢复速度比峰值容量更重要
- 基线漂移：测试期间业务流量自然波动，误判为攻击效果
- 单点方法重复测：SYN泛洪跑三遍不如三个不同方法各跑一遍
